# 统一待办接入指南

适用对象：需要「谁现在要处理什么、办完后自动消失」的业务项目，典型是审批、工单、核对这类流程类项目。
设计依据见 [ADR 0034](adr/0034-unified-todo.md)。

## 它解决什么

站内信是不可变事实，只有已读 / 未读；待办的状态却会随业务变化——单据审批完了，「待你审批」必须消失。
统一待办让业务服务把「需要某人处理的事」投递到平台，由**业务服务自己打开、自己关闭**，
处理人在平台工作台的「待办与提醒」里看到的就始终是真实的待办。

- 平台只负责「谁现在要处理什么」，**不做流程编排**：谁审批、是否会签、几级审批都由业务项目决定。
- 处理人**不能**在平台上手动把待办标记为完成，避免平台状态与业务事实分叉。
- 待办是业务状态的投影，可能短暂不一致；业务流程**不得依赖它推进状态**。

## 接入

业务项目使用 Starter 的 `TodoClient`，Spring 自动注入，不需要自己声明 Bean：

```java
@Service
public class ApprovalService {

    private final TodoClient todoClient;

    public ApprovalService(TodoClient todoClient) {
        this.todoClient = todoClient;
    }

    /** 提交审批后：通知审批人。 */
    public void submit(Approval approval, List<String> approverIds) {
        // ……保存审批单（业务事务）……
        for (String approver : approverIds) {
            todoClient.open(approver, "approval:" + approval.getNo(), "待审批：" + approval.getTitle());
        }
    }

    /** 有人通过后：关闭这个事项下所有人的待办。 */
    public void approve(Approval approval) {
        // ……更新审批状态（业务事务）……
        todoClient.close("approval:" + approval.getNo());
    }
}
```

**配置**与站内信完全相同，无需新增：

| 环境变量 | 含义 |
|---|---|
| `KAIWU_SYSTEM_SERVICE_URI` | System 的地址（`http(s)://` 或 `lb://`，见 ADR 0024） |
| `KAIWU_NOTIFICATION_DELIVERY_TOKEN` | 服务投递凭据，与站内信共用同一个值 |

缺任一项时 `TodoClient` 静默跳过，不影响启动与业务。

> `TodoClient` 随 Starter 发布。已有项目要使用它，需要把 `kaiwu-system-starter.version` 升到包含它的版本。

## 业务键 `bizKey`

`bizKey` 是**业务事项**的唯一键，由业务项目自行约定（如 `approval:2026-0001`），
不超过 128 个字符，只能包含字母、数字与 `: _ . / # -`。

- 平台以 `(项目, bizKey, 处理人)` 为幂等键：同一个键重复 `open` 只会更新标题、正文与截止时间，不会产生重复待办。
- 同一个事项的多位处理人**共用同一个 `bizKey`**，平台为每人保存一条。
- 已关闭的待办再次 `open`，会被重新打开。

## 常见流程怎么表达

| 场景 | 做法 |
|---|---|
| **或签**：多人中任何一人办完即可 | 给每位处理人 `open`（同一个 `bizKey`）；有人办完后 `close(bizKey)`，所有人的待办一起消失 |
| **会签**：每人各办各的 | 给每位处理人 `open`；每人办完时 `close(bizKey, 该处理人)`，只关闭他自己的 |
| **事项取消 / 撤回** | `cancel(bizKey)`，待办标为「已取消」而不是「办理完成」 |
| **转交 / 改派** | 对原处理人 `cancel(bizKey, 原处理人)`，对新处理人 `open(新处理人, 同一个 bizKey, …)` |
| **带截止时间** | `open(…, dueAt)`，过期后工作台显示「已逾期」并置顶 |
| **点击待办进入具体页面** | 目前点击进入本项目后台首页；页内深链接暂未支持（见 ADR 0034「暂不解决」） |

## 约定与限制

- **只在明确的业务事件后显式调用**，不要挂在请求拦截器上，也不要随每个业务请求触发。
- **失败只记日志，绝不抛出异常**：`TodoClient` 不会阻断你的业务事务，也不要用它的结果做判断。
- **打开**时处理人必须是**本项目的有效成员**，否则平台拒绝；**关闭**不要求（成员被移出后，他名下的待办仍能关掉）。
- 每个项目、每位处理人同时处于未处理的待办上限 **500**（可配置），超出会被拒绝，用来挡住失控的批量投递。
- 标题不超过 200 字，正文不超过 2000 字；`dueAt` 使用与 System 相同时区的本地时间。
- **漏发「关闭」有兜底**：平台每日清理，把超过 90 天仍未处理的待办置为已取消（无截止时间的按最后更新时间算，
  有截止时间的按逾期时间算），并物理删除关闭超过 180 天的记录。兜底只限制陈旧待办的影响时长，
  **不能代替**在业务状态变化时调用 `close`。

## 排查

| 现象 | 可能原因 |
|---|---|
| 待办没有出现 | 没有配置 `KAIWU_SYSTEM_SERVICE_URI` 或投递凭据（客户端静默跳过，只有 debug 日志）；处理人不是项目有效成员；项目未启用；业务日志里有「待办打开被拒绝」 |
| 日志出现「待办打开被拒绝 status=403」 | 处理人不是该项目的有效成员 |
| 日志出现「待办打开被拒绝 status=409」 | 该处理人未处理的待办已达上限 |
| 日志出现「被拒绝 status=401 / 503」 | 投递凭据不一致，或平台侧未配置投递凭据 |
| 办完了待办还在 | 业务代码漏调 `close`，或 `bizKey` 与打开时不一致（区分大小写）；到期后平台会兜底取消 |
