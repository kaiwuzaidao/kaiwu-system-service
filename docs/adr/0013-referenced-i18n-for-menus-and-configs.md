# ADR 0013：菜单与参数配置引用国际化资源

- 状态：Accepted
- 日期：2026-08-06
- 决策范围：`kaiwu-system-service`、`kaiwu-system-web`、`kaiwu-system-starter`
- 保留：ADR 0010 的平台国际化目录与覆盖门禁
- 修正：ADR 0010 中「菜单译文内联在 `menu_name_i18n`」的做法（仅限内置菜单）

## 背景

平台把可翻译内容分成三个桶：**资源**（`sys_i18n_message`）、**字典**、**菜单**。
资源和字典都有统一目录与批量导出/导入，唯独**菜单把译文内联在 `sys_project_menu.menu_name_i18n`**，
参数配置的展示文案则根本没有国际化能力。

由此产生两个真实问题：

1. 语言开放被卡住时，界面只能显示「菜单 2」这样的数字，**看不出是哪两个菜单**，
   要补译文得先去导出工作簿才知道对象。
2. 需要国际化的展示型配置（公告文案一类）无处可放，只能写死一种语言。

同时发现一处既有缺陷：`platform.locale` 字典项本就有 `default_item` 标记，前端也已按它推导
默认语言，**但后端把默认语言写成了常量 `DEFAULT_LOCALE = "zh-CN"`**，默认语言实际不可配。

## 决策

### 1. 引用式国际化，只用一个可空列

`sys_project_menu` 增加 `menu_name_key`，`sys_app_config` 增加 `value_i18n_key`，
均为可空 `VARCHAR(128)`。

**非空即启用，不引入布尔开关列。** 界面上仍然是「启用国际化」勾选框 + 必填的 key 选择器，
但勾选态由 key 是否为空推导。若既有开关列又有 key 列，会出现「勾了没填」「填了没勾」
「取消勾选后残留脏值」三种自相矛盾的行，而每个读取点都要同时判断两个字段——
少一个字段就少一整类 bug。

### 2. 范围：内置菜单与展示型配置

- **内置菜单**（`project_code = 'system'`）使用 key 引用。
- **业务项目菜单**继续内联 `menu_name_i18n`，不改。用户在运行期创建的菜单名无法预先登记为
  资源，这与 ADR 0010 对字典的判断同构：编译期已知的走目录，运行期录入的只能存数据。
  覆盖门禁本来也只统计 system 项目菜单，改造范围与门禁范围正好重合。
- **配置只对展示型有意义**。限额、阈值、开关一类的值参与后端校验，翻译它们没有意义，
  界面必须写明这一点。

### 3. 统一解析入口在 `I18nService`

```java
public LocalizedText resolver(String locale, boolean anonymous)
```

返回一次性目录快照，调用方用 `of(key, fallback)` 逐条解析。

放在 `I18nService` 而不是新建组件，因为 `catalog(locale, publicOnly)` 已经是所需的数据源
并带 revision 键控缓存；另起组件会让缓存与 revision 出现第二个事实源。
依赖方向保持无环：`project`、`metadata` 依赖 `i18n`，反向没有依赖。

返回快照而非逐条查询，是因为一次导航要解析十余个菜单名，逐条调用会重复查询 revision。

**菜单名解析从 SQL 移到应用层。** 现在导航查询用 `COALESCE(JSON_EXTRACT(menu_name_i18n, locale), menu_name)`
在库里解析，SQL 够不到目录缓存；继续留在 SQL 就必须再 JOIN `sys_i18n_message`，
让一条本就有五个 JOIN、每次登录都走的查询更重。

### 4. 回退链与匿名边界

统一回退链，与字典完全一致，不允许出现第二套规则：

```text
Accept-Language → 用户偏好 → 平台默认语言 → 录入原文
```

**匿名解析只允许 `public_visible` 资源。** 配置可能在未登录时被读取，若匿名路径能解析任意
key，等于开出一个免登录读取平台内部文案的接口。实现上复用 `catalog()` 既有的 `publicOnly`。

任何情况下 key 未命中都回退到录入原文（`menu_name` / `config_value`），
**绝不把 key 本身显示给用户**——那比缺译文严重得多。

### 5. 配置引用的 key 不计入覆盖门禁

门禁只统计内置菜单与 `required_resource` 资源。配置由管理员在运行期创建，若其引用的 key
计入门禁，任何管理员都能因为引用了缺译文的 key 而让整门语言掉出「可选择」，
且无从追溯是谁造成的。门禁守的是平台自己交付的内容，不是用户运行期录入的内容。

### 6. 写入时校验，不留到展示时

保存菜单或配置时，若 key 非空则必须已存在于目录，否则拒绝保存。
界面用可搜索的资源选择弹窗代替自由输入，并提供「就地新建资源」出口——
否则用户会被卡在弹窗里，只能丢弃编辑态跳去资源页。

### 7. 默认语言改读字典 `default_item`

删除常量 `DEFAULT_LOCALE`，改读 `platform.locale` 中 `default_item = 1` 的语言。
`I18nRepository.locales()` 本就在查该字典，只需增选一个字段，不引入新依赖。

**不把默认语言放进 `sys_app_config`**：解析配置需要先知道默认语言，而默认语言本身又是配置，
会形成循环依赖。

必须同步清理的硬编码（漏一处即失效）：

- `I18nRepository.missingRequiredResources` / `missingMenus` 的 `if ("zh-CN".equals(locale)) return 0;`
  ——这是「默认语言豁免覆盖门禁」的规则，**最危险**：默认语言改为 en-US 后，
  zh-CN 仍被豁免而 en-US 反被要求全量译文，判定完全颠倒。
- `I18nController` 的三处 `@RequestParam(defaultValue = "zh-CN")`。

**明确的预期边界**：更改默认语言**不会**翻译已有文案。`default_text` 存的是录入原文，
改配置那一刻它仍是原文。默认语言决定的是「回退时按哪个 locale 取译文」，
而非「把原文换成另一种语言」。

## 后果

### 正向

- 菜单与配置译文并入资源目录，复用既有的批量导出/导入，缺口在一处可见，
  不再出现「菜单 2 但不知道是哪两个」。
- 单一可空列消除了开关与值不一致的整类缺陷。
- 匿名解析有明确且复用既有机制的安全边界。
- 默认语言真正可配，且事实源唯一。

### 成本与限制

- 导航菜单名解析从 SQL 移到应用层，需保证批量解析只取一次目录快照。
- 内置菜单需一次性迁移到 key 引用（当前 13 条）。
- 业务项目菜单与内置菜单从此有两种译文来源，读取侧必须都走统一入口。
- Starter 侧**下发已解析文本，不下发 key**：`ProjectConfigClient` 读的是业务进程内的内存
  快照，够不到平台目录，下发 key 会让业务后端拿到无法翻译的值。

## 被否决方案

- **布尔开关 + 复用原列**：制造自相矛盾状态，且每个读取点要判断两个字段。
- **业务项目菜单也改为引用**：运行期创建的菜单名无法预先登记为资源。
- **解析器放在 `common/` 独立组件**：会复制目录访问与缓存，revision 出现第二个事实源。
- **默认语言存进 `sys_app_config`**：与配置解析形成循环依赖。
- **配置引用的 key 计入覆盖门禁**：把语言开放的治理权漏给每一个管理员。
- **key 未命中时显示 key**：对用户而言比缺译文更糟。
