# ADR 0001：第一天采用 Gateway 与微服务边界

- 状态：Accepted
- 日期：2026-07-23
- 决策人：Kaiwu 项目维护者

> 本 ADR 只决定运行时服务边界；仓库边界由 ADR 0002 补充。

## 背景

上一个平台从模块化单体起步，后续因真实入口治理需求补 Gateway，造成路由、认证边界和部署方式返工。新项目需要在开始写业务能力前固定入口与服务边界，避免平台再次扩张成难以拆分的进程。

## 决策

从仓库第一天起固定以下构建和运行边界：

| 单元 | 端口 | 边界 |
|---|---:|---|
| `gateway-service` | 8088 | 外部 API 入口、统一认证、会话与项目入口策略、显式路由；不写业务规则 |
| `system-service` | 8080 | 平台用户、权限、菜单、字典、配置、审计、组织和项目控制面 |
| `system-web` | 8000 | 平台管理 UI；API 必须经过 Gateway |
| `system-starter` | 无 | 业务服务 SDK；本地验证 Gateway Context 并完成接口和数据权限校验 |

补充约束：

1. 部署环境使用 Nacos 注册发现，但 Gateway 禁止 discovery locator 自动暴露服务，只允许显式路由。
2. 本地 `local` profile 可将显式路由指向 `http://127.0.0.1:8080`，用于在不启动 Nacos 的情况下验证同一入口拓扑；它不是另一种产品架构。
3. `system-service` 是平台控制面，不承载生成业务项目的 Controller、Service、Mapper 或业务表。
4. 每次代码生成得到独立后端、独立前端、独立数据库、独立 GitOps 路径。
5. 第一阶段不创建 Workflow、Integration、AI Harness、发布中心或共享部署模式。
6. 修改以上边界前，必须提交新 ADR，并给出已经发生的真实需求、现有方案无法满足的证据、迁移成本和回滚方案。
7. 认证和授权的详细信任边界由 ADR 0003 固定：System 是身份/权限事实源，Gateway 是外部认证和项目入口策略执行点，目标服务保留最终授权。

## 结果

正向结果：

- API 入口、认证和路由边界从第一天可见。
- 平台控制面与生成的业务应用保持独立部署和数据边界。
- 后续增加平台能力时不需要重新拆入口。

需要承担的成本：

- 本地开发多一个 Gateway 进程。
- 跨服务契约必须显式版本化并测试。
- Nacos 和 Gateway 配置需要作为部署必备项维护。

## 被否决方案

- 先做模块化单体、出现需求后再补 Gateway：已经导致过返工。
- 将业务项目模块共享部署到 `system-service`：破坏独立部署与独立数据边界。
- 自动发现并暴露全部 Nacos 服务：扩大攻击面，且失去路由审阅边界。
