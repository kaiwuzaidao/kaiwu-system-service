# ADR 0042：项目配置移交包与移交记录

- 状态：Accepted（已实现：只读导出、`roles.yml` 导入、授权与删除逐项确认、移交记录、`project sync --with-access`；页面在 `kaiwu-system-web` 的项目管理抽屉「配置移交」页签）
- 日期：2026-10-30
- 决策范围：`kaiwu-system-service`（清单同步、项目 i18n）、`kaiwu-system-web`（项目管理抽屉）、`scripts/kaiwu.sh`
- 补充：ADR 0036、ADR 0037；修订 ADR 0036 第 3 节「同步本身不改任何角色授权」

## 背景

ADR 0036 让业务仓里的 `kaiwu/*.yml` 成为字典、配置、菜单的事实来源，各环境执行 `project sync` 即可同步。
但存量数据与日常运营里仍有三类内容没有进入清单：

1. 早期通过网页、CLI 创建的字典、配置、菜单，当时没有对应的清单文件。
2. 运营在网页上直接新增或修改的内容，只表现为 `project sync` 计划里的"漂移"。
3. 业务角色及其授权。ADR 0036 明确不同步授权，目标环境靠人工重做，没有可核对的依据。

这些数据不能转成 Flyway：Flyway 脚本在平台仓，平台仓单向导出开源、禁止出现业务名；项目与菜单的主键在
各环境不同；在线 CRUD 的操作序列也不等于最终状态。需要一条"从某个环境取出当前状态，在另一个环境按业务键
对齐"的通道，并且留下每次移交的记录。

## 决策

### 1. 移交包是项目配置的全量快照

每次导出都是该项目配置的**全量快照**，不做增量，不依赖"哪些改过"的标记。漏掉的、手工改的内容下次导出
自然带上。目标环境按业务键逐条比对，只执行有差异的部分，重复导入同一个包结果不变。

移交包是一个 JSON 文件：

```json
{
  "formatVersion": 1,
  "projectCode": "order-center",
  "source": { "host": "kaiwu-test.example.com", "exportedBy": "7", "exportedAt": "2026-10-30T09:00:00Z" },
  "digest": "<sha256>",
  "stats": { "dicts": 12, "configs": 5, "menus": 18, "roles": 3 },
  "warnings": [ "配置 xxx 是敏感项，未导出" ],
  "files": { "dicts.yml": "...", "configs.yml": "...", "menus.yml": "...", "roles.yml": "..." }
}
```

- `dicts.yml`、`configs.yml`、`menus.yml` 与业务仓 `kaiwu/` 下的同名文件**同一格式**，可以直接覆盖进仓库提交。
- `digest` 覆盖文件名与内容，不含导出时间与来源，同一状态两次导出摘要相同；它用于完整性与"是否导入过"的判断，
  不是签名，不证明来源可信。
- 包内不含：数据库 ID、成员、密钥、敏感配置、会话、业务数据。敏感配置不导出并写入 `warnings`。
- 菜单中由平台在建项目时种入的"成员管理 / 角色授权 / 文件"节点不导出，目标项目创建时已有。

### 2. 文本的显式 i18n key

ADR 0036 的清单不手写国际化 key，由平台按规则生成。导出的数据来自网页，key 可能是运营自定义的，
按规则重新生成会让"导出再导入"产生无意义的变更。因此多语言文本增加可选字段 `i18nKey`：

```yaml
name: { i18nKey: dict.order.status, zh-CN: 订单状态, en-US: Order status }
```

- 有 `i18nKey` 且带译文：目标项目内不存在则创建，存在则保留人工译文，不覆盖。
- 有 `i18nKey` 无译文：引用平台或项目内已有的 key，key 不存在时拒绝（400）。
- 没有 `i18nKey`：沿用 ADR 0036 的生成规则。
- `i18nKey` 不是合法语言代码，不会与语言字段冲突。

### 3. 授权进入移交包，但逐项确认

ADR 0036 的理由是"授权属于安全决策，不跟随代码自动扩散"，这个原则不变。修订点是：授权可以**被携带、被展示、
被人确认后执行**，而不是只能靠人工重做。

- `roles.yml` 只含自定义角色，不含内置 `project-admin`，不含成员。授权以业务键表示：按钮用权限码，页面用路由，
  目录用 `dir:` 加名称路径，不使用菜单 ID。
- 授权类变更在计划里单独成组，**默认不执行**，需要勾选。执行方式是追加授权，不撤销目标环境已有的授权。
- 执行授权要求调用者具备项目内的角色授权权限，不因为批量入口绕过逐项权限。

### 4. 移交记录与删除提醒

只增不删的语义不变，但需要能告诉人"源环境已经删除了这些条目"。

- 目标环境每次成功导入，写一条移交记录，保存本次包里全部条目的业务键清单。
- 下次导入时做三方比对：上次包、本次包、目标当前。上次有、本次没有、目标还有的条目，列为"源环境已删除"；
  上次没有、本次也没有、目标有的条目，是目标自己加的，只列为"仅目标有"，保留。
- 删除默认不勾选，勾选后走现有删除接口，原有校验（例如角色仍有成员时拒绝）一律保留。
- 第一次导入没有基线，多出的条目一律只提示，不给出删除建议。
- 平台无法判断业务数据是否仍引用某个字典值，删除字典项时界面提示由人确认。

### 5. 实现要点

- `plan` 响应的每个条目带 `category`：`NORMAL` 随计划执行，`ACCESS` 需勾选导入授权，`DELETE` 需逐项勾选；
  动作 `REMOVED_AT_SOURCE` 表示源环境已删除。`DRIFT` 只报告。响应另带 `hasBaseline` 与 `alreadyApplied`。
- `apply` 请求带 `applyAccess` 与 `deleteKeys`（`资源|标识`，只能取自计划）。计划哈希覆盖全部条目、涉及的平台状态与基线摘要，
  与勾选无关：勾选不同不会让同一份计划失效。
- 导入授权要求项目内 `access:role:save` 与 `access:role:grant`；删除字典/字典项要求 `system:dict:delete`，
  删除配置要求 `system:config:delete`，删除角色要求项目内 `access:role:delete`，删除菜单沿用 `system:project:menu`。
- 删除按依赖顺序执行：字典项、配置、角色、菜单（由深到浅）、字典类型。菜单仍有子节点时平台拒绝删除，整体回滚。
- 授权的撤销不自动执行：目标环境多出的授权只报告，源环境撤销授权需要人在目标环境处理。
- 成功记录与业务写入同事务提交；失败记录用独立事务写入，业务写入回滚后仍保留失败原因。
- 移交记录表 `sys_project_config_handover` 保存业务键清单作为基线，不保存数据库 ID；
  记录接口 `GET .../manifest/handovers` 与 `GET .../manifest/handovers/{id}`。
- 建项目时种入的成员、角色、文件菜单不参与比对，不再作为漂移报告。
- **定时任务**（`jobs.yml`）：业务键是任务名，导入时新建的任务**一律停用**，已有任务只更新 cron、时区、任务类型与参数，
  不改启用状态。原因是调度服务要求目标项目有在线 Handler 才能新建或启用任务，而 Handler 是否在线取决于目标环境里业务服务
  是否在运行；移交后由人确认 Handler 已注册再启用，避免在生产环境立刻开跑。新建与改任务类型时目标没有在线 Handler，
  计划整体拒绝并说明原因。目标有多个同名任务时拒绝（业务键有歧义）；导出遇到同名任务时不导出并警告。
  需要平台权限 `system:scheduler:save`。任务参数（payload）按原文移交，不应放密钥。
- **国际化资源**（`i18n.yml`）：导出项目作用域内全部资源（含被字典、菜单引用的），业务键是资源 key。目标已存在而文案不同的
  按移交包更新（计划里列为更新、默认执行，与 ADR 0036 对清单译文「不覆盖人工改译」不同：移交的目的就是对齐文案，
  且逐条差异在预览里可见）。包里没有 `i18n.yml` 时不处理，也不报告漂移。字典、菜单文本里嵌入的资源仍照旧处理，
  同一个 key 在 `i18n.yml` 里给出时以 `i18n.yml` 为准。
- 删除顺序补充：字典项、配置、角色、定时任务、菜单（由深到浅）、字典类型、国际化资源。
- 命令行 `project sync` 默认不上传 `roles.yml`、不导入授权、不删除；加 `--with-access` 才导入授权；会上传 `jobs.yml` 与 `i18n.yml`。
  删除只在页面逐项确认，命令行只显示不执行。

### 6. 入口与权限

- 导出 `GET /api/projects/{projectId}/manifest/export`：只读，调用者必须是该项目的有效项目管理员，
  入口权限与 `plan` 一致（`system:project-factory:generate`）。页面入口的权限在页面 MR 中统一评估。
- 计划与执行沿用 `plan`、`apply`，扩展请求以接收 `roles.yml`、授权与删除的勾选；CLI 增加 `--with-access`。
- 所有写入经由现有的字典、配置、国际化、菜单、角色服务，审计、校验与缓存刷新与网页操作一致。

## 被否决方案

- **增量导出**：需要在所有写入入口埋点记录变更，漏一个入口就漏交付，这正是要解决的问题。
- **把在线操作转成 Flyway SQL**：违反平台仓不含业务名的约束，且 ID 与操作顺序无法跨环境复用。
- **两个环境直连互拉**：需要环境间互信与网络打通，第一期用文件移交，人可以审阅后再导入。
- **授权完全不进移交包**：目标环境没有可核对的依据，只能靠人工记忆。
- **目标环境默认删除源环境已删的条目**：平台查不到业务数据引用，误删代价高于多留一条。

## 后果

- 存量配置可以一次性导出收回，并可直接放进业务仓 `kaiwu/` 提交。
- 清单解析器新增 `i18nKey` 字段，向后兼容：旧清单不受影响。
- 后续 MR 新增 `sys_project_config_handover` 表、`roles.yml` 解析与计划、页面"配置移交"页签。
- 没有稳定键的无路由目录菜单仍按"同一父节点下的名称"匹配，存在重名风险，另立任务引入 `menu_key`。

## 迁移与回滚

- MR1 只新增只读接口与解析器的可选字段，不改变任何现有行为，回滚时下线接口即可。
- 后续新增的移交记录表只被新能力读写，回滚时下线能力，表可保留或在新版本迁移中删除。
