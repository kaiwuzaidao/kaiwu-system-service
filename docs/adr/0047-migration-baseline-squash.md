# ADR 0047：v0.2.0 前压缩一次迁移基线

- 状态：Accepted
- 日期：2026-11-12
- 范围：平台控制面的数据库迁移（MySQL 与达梦）、迁移副本、已有安装的升级路径。

## 背景

平台迁移已累积到 V1–V127。其中有不少先建后删的中间过程：一些表和配置项在后续版本被整体
移除，一些种子数据被多次改写。全新安装要把这段演进完整重放一遍，使用者读到的是开发过程，
而不是当前的数据模型。

两种数据库的起点也不一致：MySQL 从 V1 开始，达梦从 V99 基线开始（ADR 0048）。

同时存在一条既有规则：公开发布后的迁移不可修改，修正只能追加更高版本
（`sql/increment/README.md`）。v0.1.0 已带着 V1–V44 公开。压缩基线意味着改写已公开的迁移，
与这条规则直接冲突。

不压缩的代价是：v0.2.0 一旦发布，公开且不可变的迁移从 44 个变成 127 个，以后压缩的成本只会
更高。

## 决策

**在 v0.2.0 发布前，对“公开迁移不可变”破例一次，把现有全部迁移压缩为单一基线。**

破例只此一次，依据是 v0.1.0 是首个公开版本、发布时间短、尚无已知的生产使用。从 v0.2.0 起
规则恢复，见“此后的规则”。

### 1. 基线的版本号取压缩点，不回到 V1

基线文件命名为 `V127__kaiwu_baseline.sql`，127 即压缩时的最高迁移版本。之后的迁移从 V128 继续。
MySQL 与达梦使用同一个版本号 127，达梦现有的 V99 基线和 V100–V127 同样被这一个文件取代。

不回到 V1 的原因：

- 旧版本号永不复用。一个带着压缩前历史的数据库，不会把新的 V2、V3 误认成自己已执行过的
  同号迁移。
- 已有 ADR、文档和代码注释里引用的版本号（例如“V102 已落地”）仍然指向同一件事，只是它
  现在包含在基线里。
- 正在开发、已经占了 V128 及之后编号的分支不需要重新编号。
- 与达梦现有“基线版本号等于压缩点”的做法一致。

### 2. 基线从真实数据库导出，不手工拼接

起一个一次性数据库，完整执行压缩前的全部迁移，再导出结构与种子数据作为基线。两种数据库
各做一次。

基线只包含平台自身的数据。个别部署为自己的业务项目加入的展示数据不进入基线；因此导出标记
段和相应的发布忽略项随之删除，基线文件本身即可公开。

必须给出等价性证明：旧迁移全量执行得到的数据库，与新基线执行得到的数据库，逐表对比结构和
种子数据一致，唯一允许的差异是上一段排除的展示数据。对比脚本进入仓库的验证目录，可重复
执行。

### 3. 已有安装怎么办

| 安装的状态 | 处理 |
| --- | --- |
| v0.1.0（迁移停在 V44） | 不支持原地升级到 v0.2.0。需要新建数据库后重新初始化。 |
| 迁移已到 V127 | 做一次人工的迁移历史重置，数据保留。 |
| 迁移在 V44 与 V127 之间 | 先用压缩前的最后一个版本迁移到 V127，再做历史重置。 |

**历史重置**是一次性的人工操作，步骤写入 `docs/UPGRADING.md`：

1. 备份数据库。
2. 确认迁移历史的最高成功版本恰好是 127，且没有失败记录。
3. 清空迁移历史表，用 Flyway 的 `baseline` 命令写入一条版本为 127 的基线记录。
4. 用新版本执行 `migrate`，应当报告没有待执行的迁移。

这一步之所以安全，靠的是上一节的等价性证明：到达 V127 的数据库在结构上与新基线一致。

边界：

- 历史重置由操作者手工执行，不做成启动器、Helm 或迁移工具的自动行为。
- `FLYWAY_BASELINE_ON_MIGRATE` 保持 `false`；不放宽缺失迁移校验；不使用 `repair`。
  ADR 0048 对达梦迁移工具“禁止自动 baseline”的约束不变，这里的 `baseline` 是操作者显式
  执行的单条命令。

### 4. 拒绝要清楚

现有的 Flyway 兼容性检查在迁移前运行。压缩后它必须识别“数据库带有压缩前历史”这种情况，
在执行任何 DDL 之前停下，并直接告诉操作者属于上表哪一行、去读 `docs/UPGRADING.md` 的哪
一节。不能让使用者面对一条 Flyway 原始的校验错误自己猜。

### 5. 需要同步的位置

基线替换涉及同一份内容的多个副本，必须在同一次变更里一起改，并由现有的一致性检查把关：

- `sql/increment/`、`sql/dm/`；
- `sql/schema.sql`（累计快照，压缩时与基线内容一致）；
- Helm Chart 内的两份迁移副本，以及部署仓中的 Chart 副本；
- 迁移约定测试、升级夹具，以及其他按版本号断言的测试和脚本；
- 前端仓按增量目录重建目录数据的一致性检查；
- `sql/increment/README.md`、`docs/DATABASES.md`、`docs/UPGRADING.md`。

压缩时一并修正 `sql/schema.sql` 中已知的两处缺陷（一处多余的 `+`，一处重复的主键值）。

## 此后的规则

- 从 v0.2.0 起，`V127__kaiwu_baseline.sql` 及其后的迁移公开后不可修改，修正只能追加更高
  版本。
- 再次压缩基线必须另立 ADR，只能发生在主版本升级时，并且必须同时提供从上一个主版本原地
  升级的受支持路径。本次没有提供这样的路径，不构成先例。

## 后果

- 全新安装只执行一个基线文件，读到的是当前数据模型。
- MySQL 与达梦的迁移从同一个版本号起步，之后逐版本对应。
- v0.1.0 的安装无法原地升级。CHANGELOG 和 `docs/UPGRADING.md` 必须在显著位置写明。
- 压缩前的迁移文件从仓库当前树中移除，仍可从 v0.1.0 标签和版本历史中取得。
- 压缩需要一个短暂的迁移冻结窗口：窗口内不合入新的迁移。

## 考虑过但未采用的方案

- **不压缩。** 保留全部规则，但把 127 个迁移永久公开，且此后没有更低成本的时机。
- **压缩并回到 V1。** 看起来最干净，但旧版本号被复用，带旧历史的数据库可能产生难以察觉
  的错位，在途分支也要全部重新编号。
- **把旧迁移移到归档目录继续随仓库发布。** 没有解决“公开的是演进过程”这个问题，还多出一
  份无人执行的 SQL。
- **放宽缺失迁移校验，让带旧历史的数据库直接继续。** 会永久削弱迁移校验，与既有约束冲突。
- **在工具里自动 baseline。** 一次配置错误就可能让一个空库被标记为已初始化，风险与收益不
  相称。
