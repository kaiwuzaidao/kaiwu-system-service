# ADR 0015：引用式国际化是多语言的唯一入口，退役内联多语言列

- 状态：Accepted
- 日期：2026-08-07
- 决策范围：`kaiwu-system-service`、`kaiwu-system-web`
- 修正：ADR 0013 第 2 节「业务项目菜单继续内联 `menu_name_i18n`」
- 修正：ADR 0014 第 1 节「固定文案模式保留逐语言输入」

## 背景

ADR 0013 / 0014 建立了「引用国际化资源」这条路，但同时保留了内联多语言列作为并行方案：

- `sys_dict_item.label_i18n`（字典项标签的逐语言 JSON）
- `sys_project_menu.menu_name_i18n`（业务项目菜单名的逐语言 JSON）

当时保留内联的理由是「用户运行期创建的对象无法预先登记为资源」。**这个理由现在已经不成立**
——引用式国际化后来补上了「就地新建资源」，运行期创建的对象随手就能建资源，
参数配置一直就是这么做的。

保留两条路带来三个实际问题：

1. **两个真相源**。同一条字典项的英文可能在 `label_i18n` 和引用的资源里各存一份，
   改了一处另一处不动，最终显示取决于解析顺序——这与之前那个「管理页填了译文却没反应」
   的缺陷是同一种结构。
2. **实测 47 条数据在无意义地重复**：全局字典项同时有 `label_i18n` 和 `label_i18n_key`，
   且两侧 en-US 译文完全一致（差异数 0）。任一侧被改动就会漂移。
3. **界面语义混乱**。「固定文案」模式下却能填日语、英语，用户合理地感到困惑——
   该模式的真实含义是「译文存在本条记录上」，而不是「只有一种语言」。

## 决策

### 1. 多语言只有一条路：引用国际化资源

需要多语言的内容一律通过 `*_i18n_key` 引用资源目录。
「固定文案」模式退化为**单一原文**，不再提供逐语言输入。

覆盖范围：字典项标签、业务项目菜单名（与内置菜单、参数配置的既有做法拉齐）。

### 2. 内联列退役但不删除

`label_i18n` / `menu_name_i18n` 两列**保留在表结构中但不再读写**：

- 迁移把存量数据搬进资源目录后清空这两列；
- 服务端解析链从「引用 → 内联 → 原文」简化为「引用 → 原文」；
- DTO / VO 移除对应字段，界面不再提供入口。

不物理删除列，是因为删列不可逆；保留空列的成本仅是一点表宽度，
而一旦迁移有遗漏，数据还在，可以补救。

### 3. 存量迁移

- 已有 `label_i18n_key` 的字典项（实测 47 条）：内联数据与资源译文一致，直接清空。
- 有 `label_i18n` 但无 key 的（实测 2 条，均为 `platform.locale` 的语言名）：
  按 `dict.{dictCode}.{itemValue}` 建资源、搬入译文、设置 key，再清空内联。
- 业务项目菜单（实测 0 条）：同样规则处理，为将来可能存在的存量兜底。

自动创建的资源一律 `required_resource = 0`——它们来自运行期数据，
不该让某门语言因为它们缺译文而掉出「可选择」（沿用 ADR 0013 第 5 节）。

### 4. 界面措辞

「固定文案」改为「**独立填写**」，并在选项旁说明两种模式的差别是**译文存在哪**：
独立填写只维护本条原文，引用资源则多处共用、改一次全改。

## 后果

### 正向

- 多语言只有一个真相源，消灭「改了一处不生效」这一整类缺陷。
- 解析链少一层，`toItemView` 与导航菜单解析都更简单。
- 界面语义自洽：「独立填写」就是单一原文，想要多语言就去引用资源。
- 47 条冗余数据消失，不会再漂移。

### 成本与限制

- 想给一条字典项加译文，必须先建/选一条资源，比直接填多一步。
  这是有意的取舍：换来的是译文可复用、可批量导出导入、有唯一出处。
- 两列成为空的历史遗留，需在 `AGENTS.md` / 注释中说明不得再使用，
  否则将来有人看到列存在又开始写入。

## 被否决方案

- **保留内联、只是界面上隐藏**：解析链仍会读它，用户看得到却改不了，
  正是此前那个缺陷的成因。
- **固定文案填的译文自动创建资源**：那样两种模式就没有区别，
  且会让资源目录被自动生成的条目淹没，key 命名也脱离用户控制。
- **直接 DROP 两列**：不可逆，且一旦迁移有遗漏就永久丢失译文。
