# ADR 0010：平台国际化与语言边界

- 状态：Superseded by ADR 0011
- 日期：2026-08-04
- 范围：`kaiwu-system-web`、`kaiwu-system-service`；生成业务项目仅定义后续边界
- 前置：ADR 0002、ADR 0004、ADR 0006、ADR 0009

> 本 ADR 记录首版代码语言包方案及其验证过程。用户语言持久化、稳定 key、机器值不翻译和
> 历史事实不改写等边界继续有效；静态完整语言包、导航 `i18nKey` 与“暂不建设数据库资源
> 中心”的实现决策已由 ADR 0011 取代，禁止据此恢复旧链路。

## 背景

Kaiwu 当前以中文为唯一界面语言：前端关闭了 Umi Layout 的 locale，应用菜单也明确
设置为不翻译；页面文案、校验提示和下载提示直接写在组件中。菜单与字典名称来自 System
数据库，后端业务异常大多直接返回中文消息。因此，只翻译前端静态文案会形成“外壳是英文、
业务内容仍是中文”的不完整体验。

代码抽样统计也表明这不是一次机械替换（2026-08-04 实测）：

| 项 | 规模 | 影响阶段 |
|---|---|---|
| 前端 TS/TSX 含中文行 | 932 | 阶段一、二 |
| 后端领域/API 含中文行 | 817 | 阶段二 |
| `new ApiException(...)` 调用点 | 193 | 阶段二（每处需评估是否加 `messageKey`） |
| 含中文的脚手架模板 | 23 | 阶段三 |
| `new Result(...)` 直接调用点 | 2 | 契约改造成本低，其余走静态工厂 |

`ApiException` 现有签名为 `(HttpStatus, String message)`，没有 key 参数位，阶段二的主要成本
集中在此：需扩展该类并逐点迁移，而非仅改 `Result`。

国际化适合做，但应作为跨前后端的渐进式平台能力建设，不能承诺任意语言即时可用。

## 决策目标

1. 首期正式支持 `zh-CN` 与 `en-US`，以语言包扩展其它语言。
2. 语言是 System 持久化的用户偏好；用户在任意浏览器登录后都自动恢复自己的语言。
3. 静态文案、内置菜单、内置字典、日期数字、后端错误和下载内容使用一致语言。
4. 语言选择不得改变权限、项目边界、稳定状态值、19 位 ID 或鉴权协议。
5. 国际化不演变为低代码翻译平台，不破坏已生成项目的“一次生成、平台退出写入”约束。

## 首期范围与明确排除项

首期覆盖 Kaiwu 平台自身：登录、工作台、项目工厂、系统管理、公共组件、内置菜单与字典、
常用错误提示和平台生成的下载文件。

首期不包含：

- 翻译管理后台、数据库动态语言包、在线编辑或 AI 自动翻译；
- “支持所有语言”的声明；
- RTL 布局、时区切换、币种或计量单位换算；
- 自动改写已经 SUCCESS 的生成仓库；
- 让模型自由生成源码文案，或向模型开放文件和命令执行权。

## 语言选择与持久化

前端使用 `@umijs/max` 内置国际化能力和 Ant Design locale，不再引入第二套 i18n 框架。
建议配置如下：

```ts
locale: {
  default: 'zh-CN',
  baseNavigator: false,
  antd: true,
  title: true,
  baseSeparator: '-',
  useLocalStorage: false,
}
```

`sys_user.locale` 是已登录用户语言的唯一事实源。浏览器语言和 `umi_locale` 都不是用户设置，
因此关闭 Umi 的浏览器自动识别与 Local Storage 持久化。未登录时无法识别用户身份，登录页
默认以 `zh-CN` 打开，并允许仅对当前未登录页面生效的临时切换；登录成功后立即以登录响应中的
用户 locale 覆盖临时选择。用户在另一台设备或另一浏览器登录时，同样由服务端恢复，不会退回
该浏览器的默认语言。

登录后的全局右上角和个人资料页复用同一个语言选择组件。修改时先调用用户偏好 API，服务端
成功后再调用 `setLocale(locale, false)` 无刷新切换，并同步更新内存中的 `CurrentUser`；API 失败
则保持当前语言并显示安全错误。禁止通过刷新切换语言：Access/Refresh Token 只驻留内存，完整
刷新会按 ADR 0003 丢失登录态。组件不得在模块加载阶段缓存译文，确保无刷新切换能完整重渲染。

### 用户偏好数据与 API

- `sys_user` 增加 `locale VARCHAR(16) NOT NULL DEFAULT 'zh-CN'`，数据库只接受平台支持的 locale；
- 新增 Flyway 增量并同步 `sql/schema.sql`，存量用户统一初始化为 `zh-CN`；
- `CurrentUserView` 增加 `locale`，登录、刷新和 `/api/auth/me` 均返回同一值；
- 新增 `PUT /api/auth/me/locale`，请求体只包含 `locale`，服务端从 Gateway Context 取得当前
  userId，客户端不能指定目标用户；
- 修改自己的语言是已登录用户固有能力，不依赖项目角色或新增权限码；
- 只接受版本内明确支持的白名单值，首期为 `zh-CN`、`en-US`，其它值返回 400；
- 修改语言不撤销会话、不进入 JWT/Context claim，也不影响权限缓存；其它已打开会话在下次登录
  或重新查询 `/api/auth/me` 后收敛。

## 前端文案架构

语言文件放在 `src/locales`，按领域拆分并在语言入口聚合：

```text
src/locales/
├── zh-CN.ts
├── en-US.ts
├── zh-CN/common.ts
├── zh-CN/project.ts
├── en-US/common.ts
└── en-US/project.ts
```

key 使用稳定业务语义，例如 `common.action.create`、`project.generation.status.success`，禁止
以中文原文作为 key。React 组件使用 `useIntl` / `FormattedMessage`，不得在模块加载阶段缓存
已翻译字符串，否则切换语言后不会更新。

### 菜单

Layout 的 `menu.locale` 继续为 `false`。System 返回的菜单树、排序、路由和权限仍是唯一事实源，
不得为国际化维护第二棵前端菜单树。

翻译 key 按节点类型从**已有稳定标识**派生，不使用菜单 ID。19 位雪花 ID 对译者不可读
（`menu.system.9000000000000012000` 无法判断在翻什么），且实践中并非全部由设计分配——
`system` 项目的部分菜单 ID 曾在运行期手工创建，直到 2026-08-04 才固化进
`SystemProjectBootstrap`。

| 节点类型 | key 来源 | 示例 |
|---|---|---|
| `MENU` | `route_path` 去掉前导斜杠 | `/security` → `menu.system.security` |
| `BUTTON` | `permission_code` 原样 | `menu.system.system:audit:list` |
| `DIRECTORY` | 后端返回的稳定 `i18nKey` | `menu.system.directory.platform` |

选型依据（对 `system` 项目内置菜单实测）：12 个 `MENU` 全部有 `route_path` 且无
`permission_code`；39 个 `BUTTON` 全部有 `permission_code` 且无 `route_path`；`DIRECTORY`
只有 2 个且两个字段都为空，故由 System 按 Bootstrap 内置目录常量返回语义 key。
`NavigationMenuView` 增加可选 `i18nKey`：内置 DIRECTORY 返回语义常量，内置 MENU 返回由
`route_path` 派生的 key，自定义菜单返回 null。前端只消费该字段并以 API `name` 回退，不维护
第二份目录映射。`route_path` 与 `permission_code` 的稳定性已由路由契约和 `pnpm check:perm`
保障，变更它们本身就是破坏性改动。

- 语言包有 key 时显示译文，没有时回退 API 返回的 `name`；
- 用户自定义菜单始终显示录入原文，首期不增加菜单翻译表；
- 后端菜单名称不能作为翻译 key，避免改名导致语言包失效。

### 字典

内置字典按 `dict.{dictCode}.{itemValue}` 查语言包，缺失时回退服务端 label，未知字典值继续
原样显示。状态码、字典值和 API 参数保持稳定，不因显示语言变化。

### 日期与数字

展示层统一通过 `Intl` / `react-intl` 格式化日期、时间和数字；数据库、URL、请求参数和日志
仍使用既有稳定格式。时区仍遵循现有系统策略，本 ADR 不引入用户时区。

## 后端错误契约

`Result` 以兼容方式增加可选字段 `messageKey` 和 `messageArgs`，保留现有 `code`、中文安全
`message` 与 `data`：

```json
{
  "code": 400,
  "message": "项目不存在",
  "messageKey": "error.project.notFound",
  "messageArgs": { "projectCode": "demo" },
  "data": null
}
```

前端优先用 `messageKey` 本地化，语言包缺失或旧接口未返回 key 时展示 `message`。HTTP 状态、
业务 code 和异常分类保持不变。`messageArgs` 只允许安全、可展示的结构化值，禁止包含 token、
密码、连接串和内部堆栈。

迁移按高频公共异常、登录与会话、项目工厂、系统管理依次进行，不要求一次性改完所有异常。
日志保留稳定 key、参数和服务端安全消息，便于跨语言检索。

## 已持久化内容的语言边界

有一类内容在**写入时**就固定了语言，切换显示语言无法改变：审计日志的 `detail`、站内通知的
`title` 与 `content`。它们是历史事实记录，不是界面文案。

规则：

1. **已写入的行保持写入时的语言，不做回填翻译。** 审计记录被翻译等于篡改历史记录；
   通知是已送达内容，重写会与用户已读到的不一致。
2. **新增写入优先存结构化数据，由前端在展示层本地化**，而不是存一句拼好的话。
3. 因此不为这两类内容建翻译表，也不把它们纳入 `check:i18n` 的覆盖率统计。

审计日志已经具备条件：`sys_oper_log.change_json` 存的是
`[{"field","before","after"}]` 结构化数组，前端可按 `audit.field.{field}` 查语言包渲染字段名，
`before` / `after` 若是字典值则继续走 `dict.{dictCode}.{itemValue}`。**前端展示变更详情时应
优先渲染 `change_json`，`detail` 摘要只作为无结构化数据时的回退**——后者是写入时拼好的中文，
不可本地化。

新增写入侧的中文摘要（如 `AuditService.summarizeChanges`）保持现状即可：它服务于服务端检索和
日志排查，与界面语言无关，同 `Result.message` 的定位一致。

## 请求、下载与导入导出

公共 `apiRequest` 和下载请求按当前内存中的 `CurrentUser.locale` 发送 `Accept-Language`。该请求头
只影响服务端生成的人类可读内容，不是语言偏好的事实源，不得参与 Access JWT、Gateway Context、
项目权限快照或授权缓存计算。

- 页面内提示优先由前端 `messageKey` 翻译；
- 服务端生成的文件名、Excel 表头、校验报告按受支持 locale 输出；
- 同一 locale 的导出和导入模板表头必须一致；
- 导入器接受所有已发布语言版本的表头，避免用户切换语言后旧模板失效；
- 状态码、ID 等机器字段保持稳定，不能翻译后再作为导入值。

## 生成业务项目边界

平台国际化完成不等于生成项目已经国际化。若后续确有需求，应单独发布新的脚手架版本：

1. Blueprint 只能引用受约束的文案 key 或中性元数据；
2. 源码和语言文件仍由版本化模板确定性渲染，遵循 ADR 0006；
3. 只影响新生成项目；已 SUCCESS 项目不得再次生成或由平台回写；
4. 生成项目支持哪些语言，必须独立声明和验收。

## 分阶段交付

### 阶段零：用户偏好与技术路径验证（可独立交付）

在承诺翻译 932 行文案之前，先用最小切片验证方案本身能跑通：

- 新增 `sys_user.locale`、用户偏好 API，并让登录/刷新/当前用户契约返回 locale；
- 启用 Umi/Ant Design locale，关闭浏览器识别和 Local Storage 语言持久化；
- 增加登录后的语言切换组件，保存成功后无刷新应用；
- 只翻译登录页与全局布局（数十条 key）；
- 让导航 API 返回可选 `i18nKey`，打通一个 MENU 和一个 DIRECTORY。

验收必须证明：切换后登录态不丢失；当前页面和侧边栏立即切换；退出后在另一个全新浏览器登录
仍恢复该用户的语言；另一个用户不受影响；无效 locale 被后端拒绝。此阶段预计 1～2 个工作日，
产出是可独立使用的用户偏好能力。若届时判断不继续翻译全部页面，可以停止在此阶段；新增字段
和 API 保持向后兼容，不影响现有中文界面。

### 阶段一：基础设施与首次体验

- 建立 key 规范、语言包目录、公共格式化与回退策略；
- 覆盖工作台、项目开通/生成最短路径；
- 覆盖这些路径使用的内置菜单和字典；
- 此阶段只能称“核心流程支持英文”，不能称整个平台已英文化。

### 阶段二：平台完整覆盖

- 迁移其余平台页面、公共组件、校验与空状态；
- 为稳定 API 异常增加 `messageKey`；
- 覆盖 Excel、下载文件与校验报告；
- 完成全量双语 E2E 后，才对外声明平台支持英文。

### 阶段三：可选的生成项目国际化

只有出现明确业务需求时，才通过新模板版本为未来项目提供国际化骨架；不与平台阶段一、二
捆绑，不修改既有生成仓库。

## 质量门禁与验收

新增 `pnpm check:i18n`，至少校验：

- `zh-CN` / `en-US` key 集合一致；
- 插值占位符一致；
- 内置菜单和纳入范围的字典均有翻译；
- 纳入范围的页面不得出现硬编码的用户可见文案。

**硬编码检测必须先界定范围，否则门禁不可用。** 本仓库的工程规范要求中文注释、中文
Javadoc 与中文 commit，代码中存在大量与界面无关的中文。检测规则：

| 判定为违规（用户可见） | 明确豁免（与界面语言无关） |
|---|---|
| JSX 文本节点 | `//`、`/* */`、`{/* */}` 注释 |
| `title` / `label` / `placeholder` / `message` / `description` 等文案属性 | `console.*`、日志、错误堆栈 |
| `message.success()` / `Modal.confirm()` 等提示调用的文案实参 | 测试文件、脚本、`*.md` |
| `Popconfirm` 的 `title` / `okText` / `cancelText` | 字典 fallback 文件（`src/dictionaries/`，其内容本身就是受管语言数据） |

按 AST 判定，不要按"整行是否含中文"判定——后者会把中文注释全部判为违规。首版可只覆盖
`src/pages` 与 `src/components`，并支持 `// i18n-ignore-next-line` 逐行豁免，避免一次性
阻塞既有 932 行含中文代码。

后端不设中文检测：`Result.message`、日志与异常摘要按设计保留服务端语言，
`messageKey` 的覆盖率通过契约测试而非静态扫描保证。

E2E 至少覆盖两种语言下的登录、菜单导航、首次项目引导、项目生成、权限拒绝和会话失效；
验证切换过程不刷新且登录态仍有效，退出后在全新浏览器重新登录可恢复服务端偏好，缺 key 可
安全回退，19 位 ID、权限码和请求参数完全不变。

阶段二验收还需抽查 Excel 往返、下载文件名、后端参数化错误，以及服务端用户偏好覆盖未登录
临时选择的优先级。文档改动使用链接/静态检查验证；实施时前端仍必须通过 `pnpm typecheck`、
`pnpm build` 和既有权限/字典门禁，后端契约变更必须通过 `mvn verify`。

## 风险与控制

| 风险 | 控制措施 |
|---|---|
| 只翻译页面外壳，菜单/错误仍为中文 | 将菜单、字典、错误和下载纳入同一验收阶段 |
| 翻译 key 与数据库名称耦合 | 导航 API 返回稳定语义 key，字典使用 code + value |
| 切换语言后组件残留旧文案 | 无刷新切换，不缓存模块级译文，并用 E2E 覆盖常用组件 |
| 双语长期漂移 | CI 校验 key、占位符和内置元数据覆盖率 |
| 导入模板因语言切换失效 | 导入兼容所有已发布表头，机器值保持稳定 |
| 范围扩张为在线翻译平台 | 首期仅版本化语言包，动态管理另行立项与 ADR |
| 误改已生成仓库 | 生成项目只通过未来模板版本演进 |
| 硬编码检测误伤中文注释导致门禁被关掉 | 按 AST 判定用户可见文案，注释/日志/测试豁免，支持逐行 ignore |
| 菜单 key 随手工建菜单漂移 | System 只为内置节点返回稳定 `i18nKey`，自定义菜单回退原名 |
| 浏览器切换只在本机生效 | `sys_user.locale` 是事实源，登录/刷新/当前用户响应统一返回 |
| 完整刷新导致内存会话丢失 | 只允许 `setLocale(locale, false)`，切换 E2E 必须断言会话仍有效 |
| 历史审计与通知被回填翻译，篡改事实记录 | 已持久化内容保持写入时语言，新增写入优先存结构化数据 |
| 为"应该有"而投入，收益与自用目标不匹配 | 先做阶段零验证实物，再决定是否铺开 |

## 被否决的方案

1. **只启用 Layout 自动菜单翻译**：菜单由 System 动态返回，无法覆盖字典、错误和文件。
2. **以中文原文作为语言 key**：文案调整会导致 key 和翻译大面积失效。
3. **首期建设数据库翻译中心**：增加权限、缓存、审计和发布复杂度，当前没有真实需求支撑。
4. **后端只根据语言返回单一 message**：前端难以稳定回退，日志和自动化测试也失去稳定语义。
5. **一次性宣称多语言完成**：会掩盖长尾页面和服务端内容未覆盖的问题。

## 采纳前置条件

维护者已确认首批语言为 `zh-CN`、`en-US`，并确认语言必须跟随 System 持久化的用户设置，
而不是浏览器本地偏好。本 ADR 因此进入 Accepted。

阶段零会修改数据库和登录/当前用户 API，必须作为独立可回滚交付；不得混入当前尚未收口的
项目工厂、权限校验和审计变更。开始编码前，四仓现有改动必须先分别形成可验证提交并记录
基线；国际化再从该基线单独提交。

进入阶段一（开始成规模翻译）前需：

1. 阶段零已跑通并确认继续投入；
2. 国际化范围和分阶段验收已补入 `docs/REQUIREMENTS.md`；
3. 阶段零先覆盖用户 locale、导航 `i18nKey` 与 Gateway 透传 `Accept-Language` 的契约测试；
   阶段二增加 `Result` 可选字段契约测试
   （`Accept-Language` 不在 `TrustedHeaderSanitizerFilter` 的清洗名单内，当前已可透传，
   契约测试用于锁定该行为）；
4. 先落 `check:i18n` 基础门禁，再迁移页面。

### 关于投入产出的前提

平台国际化的收益主要面向平台使用者中的非中文读者，对以中文为工作语言的维护者本身收益有限。
维护者已决定先实施阶段零；是否继续阶段一，依据阶段零的跨浏览器实物体验和实际迁移工作量
再次确认，避免仅因框架支持国际化就一次性铺开全部页面。
