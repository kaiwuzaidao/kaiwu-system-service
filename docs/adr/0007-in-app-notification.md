# ADR 0007：站内信集中存储与业务服务单向投递

- 状态：Accepted
- 日期：2026-07-24
- 决策范围：`kaiwu-system-service`、`kaiwu-system-web`、`kaiwu-system-starter`、生成项目

## 背景

平台已经产生了需要主动告知用户的事实：项目生成成功或失败、GitLab 初始推送完成、
密码被重置导致会话撤销、项目成员与角色变更。这些目前只能靠用户自己去对应页面轮询。
生成的业务项目同样会产生需要通知责任人的业务事件。

站内信的价值在于**统一收件箱**：用户在一个地方看到所有项目的消息。这与
ADR 0002「新业务项目独立数据库」存在张力——收件箱按人聚合，天然跨项目。

同时 ADR 0003 规定「正常业务请求不得由 Starter 同步回调 System」，Starter 至今
没有任何对 System 的出站调用。引入站内信意味着新增「业务服务 → System」这一信任方向，
必须明确边界，避免它退化成第二条鉴权回调链路。

## 决策

1. **消息集中存储在 System 库**的 `sys_notification`，按 `recipient_user_id` 聚合。
   业务项目不再各自维护站内信表，用户只有一个收件箱。

2. **消息是不可变事实**。只允许新增，以及由收件人翻转自己的 `read_at`。
   不提供编辑正文、不提供代替他人已读、不提供撤回。

3. **读取走 Gateway，使用用户身份**：
   - `GET /api/current/notifications`：分页查询我的消息。
   - `GET /api/current/notifications/unread-count`：未读数，供顶栏铃铛轮询。
   - `PUT /api/current/notifications/{id}/read`、`PUT /api/current/notifications/read-all`。

   这些接口只操作 `StarterContext` 里的当前用户，**不接受 userId 参数**，
   因此不需要额外权限码即可访问自己的收件箱。

4. **写入是服务端到服务端的单向投递**，与用户请求链路分离：
   - Starter 新增 `NotificationClient`，业务服务显式调用发送，
     不挂在请求拦截器上、不随每个业务请求触发。
   - 投递失败必须降级为记录日志，**不得阻断业务事务**。站内信是尽力而为的通知，
     不是业务一致性的一部分。
   - 该客户端只允许调用站内信投递端点，不得用于查询身份、权限或任何授权判断。
     ADR 0003 的「Starter 不回调 System 做鉴权」保持不变。

5. **投递端点的信任边界**：`POST /api/internal/notifications` 只接受携带
   服务凭据的调用，不经 Gateway 的用户鉴权链路，且必须在网络层限制为内部可达。
   端点接受 `projectCode` 标识来源项目，System 校验该项目存在且启用；
   `recipientUserId` 必须是该项目的有效成员，否则拒绝投递——
   防止任一业务服务向平台全体用户群发。

6. **平台自身产生的消息**直接在 System 内部写库，不走上面的 HTTP 端点。

7. 消息分类使用 V1 基线中的受管字典 `notification.type`
   （`SYSTEM` / `PROJECT` / `TASK`），页面不硬编码枚举。

8. 本能力**不做**：外部渠道（邮件、短信、企业微信、Webhook）、消息模板与变量渲染、
   订阅偏好、群发与定时发送、已读回执统计、消息中心的富文本编辑。

## 后果

- 用户在平台后台和任意业务后台都能看到同一个收件箱，收件箱是跨项目的单一事实。
- 新增了「业务服务 → System」的信任方向。这是本 ADR 的核心代价，因此把它限制成
  一个只写、单向、失败即降级、且与鉴权无关的窄接口，避免侵蚀 ADR 0003。
- 业务项目的独立数据库约束不变：业务数据仍在自己库里，只有"通知这件事"集中。
- 投递端点必须靠部署时的网络隔离保护。若未来要暴露到不可信网络，需要新 ADR
  引入正式的服务身份（如 mTLS 或签发给服务的短期凭据），本阶段不做。
- 站内信不保证送达，业务侧不得依赖它做流程流转或状态机推进。
