# ADR 0038：平台只做确定性脚手架，业务代码交给 AI 工具

- 日期：2026-10-29

## 背景

ADR 0006 起，项目工厂有三种生成模式：`AI_PROJECT`（平台调用自己配置的模型，按描述生成数据模型和后台模块）、
`DDL_SCAFFOLD`、`BASIC_SCAFFOLD`（确定性模板渲染，不用 AI）。ADR 0035 之后，用户的 AI 编程工具
（Codex、Trae、CodeBuddy、Claude Code 等）已经能通过 CLI 登录平台、生成并取回项目、同步清单。

这使平台侧的 AI 生成成了重复建设：

1. 用户的 AI 工具本来就在写代码，且在本机，能读完整仓库、跑测试、迭代；平台侧一次性生成做不到。
2. 平台要为此配置并维护模型服务商、网络策略、提示词和结果校验，成本和故障面都在平台。
3. 生成结果只是"第一版"，之后总要由 AI 工具接着改；两套 AI 的产出风格不一致。
4. 把 Git 仓库推送与项目体检建立在 GitLab 访问之上，也违背"用户自己决定代码放在哪里"的方向：
   第一版推送后，后续 CI/CD 与分支策略本来就由业务仓库接管。

平台真正不可替代的是：项目登记、权限与菜单、确定性的工程骨架（CI、部署、网关路由、约束文件、`AGENTS.md`），
以及清单同步这类需要平台数据的动作。

## 决策

### 1. 平台只保留确定性脚手架

- 保留 `BASIC_SCAFFOLD`、`DDL_SCAFFOLD` 与 MySQL 表结构导入；它们不调用模型，同样输入产出同样仓库。
- `DDL_SCAFFOLD` 的 DDL 由用户或其 AI 工具提供；平台只据此渲染骨架与基础 CRUD。
- 下线 `AI_PROJECT`：创建接口与页面不再接受该模式，`AiMetadataEnhancer`、`ProjectGenerationAiAdapter`
  与相关提示词、校验代码一并删除。已存在的 `AI_PROJECT` 任务保留为历史记录，仍可查看和下载。
- **AI 服务商配置保留**：平台自身的 AI 助手（Agent）仍使用它，本 ADR 只是不再用于生成项目。

### 2. 业务代码由 AI 工具在本机完成

- 平台的职责到"生成并下载仓库"为止；之后由 AI 工具按仓库里的 `AGENTS.md`、
  `docs/kaiwu-constraints.json` 与 `docs/kaiwu-project-blueprint.json` 继续开发，并运行项目自带的校验。
- 这些约束与校验必须足够严格，才能兜住 AI 的产出：项目 CI 与本地校验脚本使用同一份约束；
  新增约束先落到模板与校验脚本，再要求业务仓库升级模板。
- 模板版本升级仍由平台提供，业务仓库按需合并，不再依赖"重新生成"。

### 3. 模板自带清单与本地校验入口

- 生成的仓库带 `kaiwu/` 清单目录（ADR 0036 第二阶段），字典、配置、菜单、文案随代码一起版本化，
  通过 `./kaiwu project sync` 同步；`sql/menu.sql` 与 `import-project-menu` 旧路径随之移除。
- 提供一个本地校验入口，AI 工具在提交前运行，覆盖权限码三处一致、字典与清单一致、约束文件检查。

### 4. 去掉 GitLab 推送与只读体检

沿用此前"CLI 就绪后移除"的决定：

- 下线 `/api/project-generations/{taskNo}/push`、`ProjectGenerationGitAdapter`、`GitlabApiClient`、
  GitLab 配置（控制器、服务、实体、页面）与 `ProjectHealth` 体检（它依赖 GitLab 读取）。
- 保留 ZIP 下载与 CLI `project pull`；用户自行推送到任意 Git 服务，或让 AI 工具推送。
- 相关数据库表本期**不删除**：先停用代码并保留一个版本，表的清理另起一次迁移并单独确认（见"迁移与回滚"）。

### 5. 分阶段落地

| 阶段 | 内容 | 可独立回滚 |
|---|---|---|
| 1 | 停用 `AI_PROJECT` 创建入口（接口校验与页面表单），保留历史任务 | 是 |
| 2 | 删除 AI 生成代码；下线 GitLab 推送、配置与体检（代码与页面） | 是 |
| 3 | 模板自带 `kaiwu/` 清单与本地校验入口；移除 `sql/menu.sql` 旧路径 | 是 |
| 4 | 清理不再使用的表与字典（单独迁移，需确认） | 视备份而定 |

## 被否决方案

- **保留 `AI_PROJECT` 作为可选项**：平台仍要维护模型配置、提示词与校验，且产物与 AI 工具的后续修改风格不一致；
  可选项意味着永远删不掉。
- **连脚手架也交给 AI 工具生成**：骨架不可复现，约束、CI、部署、网关路由与权限码一旦写错要到部署后才暴露，
  模板升级和批量修约束也无从统一。
- **继续保留 GitLab 推送，只降低优先级**：第一版推送之后平台不再参与；保留意味着长期维护连接器与体检。

## 后果

- 平台不再依赖模型服务商来开通项目，开通更快、更稳、零模型成本；AI 助手功能不受影响。
- 业务代码质量由"约束文件 + 本地校验 + CI"兜底，约束覆盖面成为关键，需要在阶段 3 前盘点。
- 已有的项目工厂页面、菜单文案、字典项和文档需要同步调整，对外"AI 受控生成"的说法改为
  "确定性模板 + 用户的 AI 工具"。
- 依赖 GitLab 推送与体检的现有用户需要改为下载 ZIP 或使用 CLI 取回。

## 迁移与回滚

- 阶段 1 只收紧创建校验与页面，历史数据不动，回滚即放开校验。
- 阶段 2 删除代码前先确认没有定时任务、Agent 能力或其他模块引用被删类型（Agent 的项目生成能力会受影响，需随之调整）。
- 阶段 4 的删表属于数据库结构变更，必须先备份并获得单独确认；在此之前所有表保留，代码回滚即可恢复功能。
- 回滚本 ADR 的整体决定意味着重新引入模型生成与 GitLab 连接，应当作为新的 ADR 处理。
