# ADR 0034：统一待办——业务服务向平台投递可关闭的待办

- 状态：Accepted
- 日期：2026-10-23
- 决策范围：`kaiwu-system-service`、`kaiwu-system-web`、`kaiwu-system-starter`、项目工厂模板及接入平台的业务项目
- 补充：ADR 0003、ADR 0007

## 背景

ADR 0007 已经把站内信做成跨项目的统一收件箱：业务服务经 Starter 的 `NotificationClient`
单向投递，System 集中存储，平台后台与各业务后台的铃铛读的是同一份数据。

「待办」还没有统一。工作台的「待办与提醒」是前端按平台自己的数据现算的（未读消息、生成失败、
待推送、AI / GitLab 未配置），业务项目没有任何途径把「需要某人处理的事」送进来。

后续会新增流程类项目（审批、工单、核对等），它们的核心诉求就是「谁现在需要处理什么，办完后自动消失」，
所以待办必须是**与具体业务无关的通用能力**，而不是为某个项目定制。

站内信不能直接充当待办。ADR 0007 规定消息是不可变事实：只有已读 / 未读，不能由来源方撤回或关闭。
而待办的核心是**状态会随业务变化**：单据审批完成后，「待你审批」必须自动消失；
用户「已读」一条待办并不代表事情办完了。

## 决策

1. **新增独立的待办模型，与站内信并列**，集中存储在 System 库的 `sys_todo`：
   来源项目 `project_id` / `project_code`、业务唯一键 `biz_key`、收件人 `recipient_user_id`、
   标题、正文、平台内链接、状态（`OPEN` / `DONE` / `CANCELLED`）、可选截止时间 `due_at`、
   打开与关闭时间。唯一约束为 `(project_code, biz_key, recipient_user_id)`。
   一个业务事项可以同时有多位处理人：每人一行，业务键相同。

2. **待办状态由来源服务拥有**。业务服务通过两个幂等操作维护它：
   - **打开**：按 `(项目, 业务键, 收件人)` 新建或重新打开；同一键重复投递只更新标题、正文、链接与截止时间，
     已关闭的会被重新打开。
   - **关闭**：按 `(项目, 业务键)` 把待办置为 `DONE`（办理完成）或 `CANCELLED`（事项取消）。
     `recipientUserId` 可选：**不传则关闭该键下所有收件人的待办**（或签：一人办完，其他人的同时消失）；
     **传了则只关闭该人的**（会签：每人各办各的）。对已关闭或不存在的待办重复关闭不报错。

   收件人**不能**在平台上把待办标记为完成，避免平台状态与业务事实分叉。
   业务事实以来源项目的库为准，待办只是它的投影。

3. **写入沿用 ADR 0007 的信任边界**，不新增信任方向：
   - System 新增 `POST /api/internal/todos`（打开）与 `POST /api/internal/todos/close`（关闭），
     使用与站内信**同一个**服务投递凭据与校验实现，由 Gateway 的内部端点过滤器阻断外部访问；
   - `projectCode` 必须对应启用中的项目；**打开**时 `recipientUserId` 必须是该项目的有效成员，
     **关闭**只会减少待办，不要求收件人仍是成员（成员被移除后其待办仍应能被关掉）；
   - 链接必须是平台内以单个 `/` 开头的安全路径（与站内信同一校验）；**缺省时 System 自动补成
     `/workspace/{项目ID}`**，因为业务服务并不知道自己的项目 ID，却需要「点击待办进入该项目后台」；
   - 单个项目、单个收件人的 `OPEN` 待办数量设上限（默认 500，可配置），超出拒绝，防止灌入。
     已处于 `OPEN` 的同键更新不占用额度。

4. **Starter 新增 `TodoClient`**，提供 `open` 与 `close`（含按收件人关闭）。与 `NotificationClient` 一样：
   不挂在请求拦截器上，只在明确的业务事件中显式调用；失败只记日志，**不得阻断业务事务**；
   不承载任何鉴权语义，也不得用于查询身份或权限；复用站内信的 System 地址与投递凭据配置，
   缺任一项时静默跳过。

5. **读取走 Gateway，使用用户身份**：
   - `GET /api/current/todos`：分页查询我的待办，默认只返回 `OPEN`，可按来源项目筛选；
   - `GET /api/current/todos/summary`：未处理数量、逾期数量与最近几条，供工作台使用。

   与站内信一样只操作当前登录用户，不接受 userId 参数，不需要额外权限码；Gateway 的
   `/api/current/**` 路由已覆盖，无需新增路由。逾期由服务端按当前时间计算，客户端不自行判断。

6. **工作台「待办与提醒」合并两类来源**：前端现算的平台待办（配置未就绪等）保留，
   再加上 `/api/current/todos/summary` 返回的业务待办，标出来源项目与逾期状态。
   平台自身的异步事件（如项目生成失败）可后续改为同样写入 `sys_todo`，本 ADR 不要求一次迁移。

7. **清理**：由平台每日定时任务（沿用审计日志清理的 Redis 锁与分批删除方式）执行两件事，作为业务服务
   漏发「关闭」时的兜底，并限制表的增长：
   - 把 `COALESCE(due_at, updated_at)` 早于 90 天前的 `OPEN` 待办置为 `CANCELLED`
     （无截止时间的 90 天未更新；有截止时间的逾期 90 天）；
   - 物理删除关闭超过 180 天的 `DONE` / `CANCELLED` 记录。

   保留期与上限均可配置。仍在有效期内的逾期待办保留并标为逾期，不自动关闭。

8. 本能力**不做**：指派与转交、多级审批编排、提醒升级与催办、外部渠道（邮件、短信、企业微信）、
   待办模板、跨项目批量操作、待办评论。流程编排属于业务项目；平台只负责「谁现在要处理什么」。

## 后果

- 用户在一个地方看到所有项目里需要自己处理的事，并且事情办完后待办会自动消失。
- 流程类项目接入只需要两个调用：事件发生时 `open`，办完时 `close`；或签与会签都能表达。
- 业务服务多了一件需要维护的事：在状态变化时调用打开或关闭。漏调「关闭」会留下陈旧待办，
  由第 7 条的兜底清理限定影响时长。
- 待办是业务状态的投影，可能短暂不一致（投递失败、网络延迟）；业务侧不得依赖它推进流程。
- 「业务服务 → System」的信任方向仍限定为 ADR 0007 的窄接口：只写、单向、失败即降级、与鉴权无关。
  若将来投递端点需要暴露到不可信网络，同样需要新 ADR 引入正式的服务身份。

## 实施拆分

1. System：`sys_todo` 迁移、内部写入端点、当前用户读取端点、清理任务、i18n（含工作台文案）。
2. Starter：`TodoClient` 与测试。
3. 平台前端：工作台「待办与提醒」合并业务待办，显示来源项目与逾期。
4. 项目工厂模板：生成项目的说明文档补充 `TodoClient` 用法（Starter 发布后随模板版本升级）。

## 暂不解决

- **深链接到业务后台内的具体页面**。目前待办链接只能到项目后台首页（`/workspace/{项目ID}`），
  `/workspace` 宿主页还不支持向子应用传入页内路径；需要时另立变更，避免现在放开任意路径。
- 业务后台内的「我的待办」页面：数据已可经 `/api/current/todos` 读取，展示留给各业务后台按需实现。
