# Flyway 迁移

- `V1__kaiwu_baseline.sql` 是 Kaiwu 全新项目的完整数据库基线。
- 下一次数据库变化从 `V2__description.sql` 开始追加，并同步更新 `../schema.sql`。
- 历史开发库若保留了基线压缩前的更高版本记录，由应用内置数据校准兼容；不得放宽
  Flyway 的 missing migration 校验，也不得对公开基线执行 repair。
- 公开发布后的 migration 不可修改；修正只能追加更高版本。
- 本基线不兼容旧开发数据库，切换时应重建数据库。
- 迁移必须确定、前向并在真实 MySQL 上验证；不要求所有版本可重复执行。普遍使用
  `IF NOT EXISTS` 会掩盖错误存量结构。只有启动自举、repeatable migration 或明确需要重试的
  seed/补偿步骤才要求幂等，并在脚本中说明原因。

## ID 分段约定

平台 seed 用 19 位 BIGINT 字面量做主键。**新增 seed 一律从 `92…` 段起（>= 9200000000000000000）**，
由 `MigrationConventionTest` 强制。

为什么要换段——V27 事故（2026-08-07）：

- V26 用 `9100000000000003100 + ROW_NUMBER() OVER (...)` 给项目菜单资源分配 ID，
  **占用长度取决于运行库里有多少行数据**，从 SQL 文件里读不出来。
- 给 V27 挑号时扫描文件中的最大字面量（`…3002`），据此选了 `…3101`——正好落在 V26 的动态段。
- `ON DUPLICATE KEY UPDATE` 撞主键后走了更新分支：把两条真实的菜单名资源覆盖成了错误码文案，
  而 V27 真正想种的两条资源**根本没插进去**；`flyway_schema_history` 里 V27 记录为成功。
- 由 V28 复原，并从此改用独立地址段。

配套规则：

- **回引已有的 `91…` ID 不受限**——修复类迁移必须能引用被写坏的旧 ID。
- 判重方式是「这个 `91…` 字面量在更早的迁移里出现过吗」，没出现过就算新造。
- 已发布的 V 脚本一律不可修改；发现问题只能追加更高版本纠正（CLAUDE.md）。
- 版本号唯一、文件名可被 Flyway 解析，同样由 `MigrationConventionTest` 在 `mvn verify` 里检查。
